# ADR-0004: Statement Exports — Async Jobs, Streaming Upload, Threshold-basierte Remote Targets

## Status
Proposed (2026-04-10)

## Kontext

LRSolid soll Statement-Exports nach Filterkriterien anbieten (Organisation, Project, LRS, Client, optional Zeitraum/Verb/Actor/Object).  
Die Exportgröße kann mehrere GB erreichen.

Risiken bei naiver Umsetzung (synchrone HTTP-Downloads + lokale Tempfiles):
- Request-Timeouts bei großen Datenmengen
- Hoher lokaler Speicherbedarf auf dem LRS-Host
- Risiko von Out-of-Disk bei parallelen Exporten
- Schwache UX (Browser-Download bricht ab, kein Resume/Retry, kein Fortschritt)

Zusätzliche Produktanforderung:
- Ab einer konfigurierbaren Größe muss der Nutzer ein Zielsystem definieren (Google Drive, OneDrive, iCloud, S3-kompatibel), um lokalen Speicherverbrauch zu vermeiden.

## Entscheidung

Wir implementieren Exporte als **asynchrone Export-Jobs** mit **streamingbasierter Erzeugung und Upload**.

Kernpunkte:
1. Export wird per API-Job gestartet (nicht synchron als Download im Request).
2. Export-Daten werden **gestreamt** (chunked), optional komprimiert (`.gz`), ohne mehr-GB Zwischenablage auf lokaler Platte.
3. Ab konfigurierbarem Schwellenwert (`require_remote_target_above_bytes`) ist ein **Remote Target verpflichtend**.
4. V1 unterstützt primär **S3-kompatible Targets**; weitere Provider folgen schrittweise.

## Architektur

### Export Job Modell

Neue Entität `export_jobs` (vereinfacht):
- `id`
- `org_id`
- `created_by_user_id`
- `filters` (jsonb)
- `format` (`ndjson`, später ggf. `csv`, `parquet`)
- `compression` (`none`, `gzip`)
- `estimated_bytes`
- `status` (`queued`, `running`, `completed`, `failed`, `canceled`)
- `rows_exported`, `bytes_written`
- `target_type` (`local`, `s3`, `gdrive`, `onedrive`, ...)
- `target_config_ref`
- `artifact_ref` (z. B. S3 key / provider file id / presigned URL metadata)
- `error_message`
- `created_at`, `started_at`, `finished_at`

### Ablauf

1. UI öffnet Export-Dialog und setzt Filter.
2. API schätzt Exportgröße (Approximation) und validiert Policy.
3. Falls `estimated_bytes > threshold`: Remote Target muss gesetzt sein.
4. Job wird erstellt (`queued`).
5. Worker verarbeitet Job:
   - liest Statements in Batches (keyset/cursor, kein OFFSET),
   - serialisiert in Ziel-Format,
   - komprimiert on-the-fly (`gzip`),
   - streamt direkt in Target-Upload.
6. UI pollt Jobstatus und zeigt Download-/Open-Link bei `completed`.

### Storage-/Memory-Verhalten

- Kein mehr-GB Tempfile erforderlich.
- Nur kleiner, begrenzter Puffer (RAM) für Streaming-Chunks.
- Ziel ist „zero large local disk dependency“ für große Exporte.

## Threshold-Policy

Konfigurierbare Settings:
- `export_local_max_bytes`
- `require_remote_target_above_bytes`

Semantik:
- Unterhalb Schwelle: lokaler Export kann erlaubt sein.
- Oberhalb Schwelle: API lehnt Job ohne Remote Target ab (`400 policy violation`).

## Targets

### V1
- **S3-kompatibel** (AWS S3, MinIO, R2, Wasabi, ...)
  - Multipart Upload
  - robust bei großen Dateien
  - gut automatisierbar im Self-hosting

### V2+
- Google Drive (resumable upload)
- OneDrive (upload sessions)
- iCloud Drive nur wenn ein stabiler serverseitiger Uploadpfad verfügbar ist.

## Format/Kompression

Standard für große Exporte:
- `ndjson.gz`

Begründung:
- stream-freundlich
- gute Kompressionsrate
- robust bei sehr großen Datenmengen
- einfach zu konsumieren in ETL/Analytics Pipelines

ZIP ist optional möglich, aber kein Muss in V1.

## Warum kein Kafka-Pflichtbestandteil

Für Export-Jobs ist Kafka **nicht zwingend erforderlich**.  
Asynchrone Worker + DB-Job-Tabelle reichen für V1 aus.

Kafka kann später sinnvoll sein, wenn:
- mehrere voneinander unabhängige Export-/Processing-Consumer parallel laufen,
- sehr hohe Joblast + horizontale Skalierung + Replay-Anforderungen bestehen,
- Export-Subsystem als eigenes Event-getriebenes Modul betrieben wird.

## Konsequenzen

### Positiv
- stabil bei Multi-GB Exports
- keine langen blockierenden HTTP-Requests
- deutlich geringeres Out-of-Disk Risiko
- klare Policy-Durchsetzung je Organisation
- besseres UX durch Fortschritt/Status

### Negativ / Trade-offs
- höhere Implementierungskomplexität (Job-Lifecycle, Retry, Provider-Handling)
- eventual consistency beim Jobstatus
- zusätzlicher Betriebsaufwand für Target-Credentials/Secrets

## Sicherheits-/Betriebsaspekte

- Target-Credentials verschlüsselt speichern (Secret-Store/KMS).
- Download-Links kurzlebig (presigned, TTL).
- Concurrency-Limits pro Org/User.
- Quotas pro Org (max Jobs/Tag, max Bytes/Tag).
- Audit-Log für Exportstart/-abschluss/-download.

## Implementierungsphasen

1. V1: Job-API + Worker + `ndjson.gz` + S3 Target + Threshold-Policy.
2. V1.1: Local Export nur unterhalb Schwelle + Retention/Cleanup.
3. V2: Google Drive + OneDrive.
4. V3: Optionale Kafka-Entkopplung bei Skalierungsbedarf.
