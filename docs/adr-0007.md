# ADR-0007: xAPI 1.0.3 and 2.0 on one LRS

## Status
Accepted (2026-10-09).

## Context

LRSolid previously exposed only `POST` and `GET /xapi/statements`, without the version header, without statement validation, and without the State, Profile, Activity, Agent, or Attachment resources. The storage ports for documents and attachments already existed for PostgreSQL and MongoDB. xAPI 2.0 is backwards compatible with 1.0.3: the same resources stay, and 2.0 adds version negotiation, `contextAgents` / `contextGroups`, and stricter signature checks.

## Decision

One `/xapi` surface serves both versions.

- `X-Experience-API-Version` is required. `1.0` and `1.0.x` negotiate to `1.0.3`. `2.0` and `2.0.x` negotiate to `2.0.0`. The response header is the negotiated version. `GET /xapi/about` lists both and does not require authentication.
- `XAPI_LEGACY_COMPAT=true` (default `false`) restores the previous tolerance: a missing version header, form-encoded statement bodies, the `{statements: [...]}` wrapper, and an extra `cursor` field next to `more`.
- Clients keep the historical scope names `statements:read` and `statements:write`. Those are aliases of `statements/read` and `statements/write`. The spec scopes `all`, `all/read`, `statements/read/mine`, `state`, `profile`, and `define` are accepted as well. `statements/write` without `statements/read` can read only statements stored for that client.
- Document `PUT`, `POST`, and single-document `DELETE` on an existing record require `If-Match` or `If-None-Match`. A missing concurrency header is `409`. A failed precondition is `412`. `POST` merges JSON objects and rejects non-JSON content with `400`.
- Statement conflicts compare documents while ignoring `stored`, `authority`, and `timestamp`, which the LRS assigns. A different document with the same id is `409`. Voiding a voiding statement is `403`.
- Attachment bytes are written under `XAPI_ATTACHMENT_DIR` (default `data/xapi-attachments`). Metadata stays in `AttachmentStore`. Object storage can replace the directory later without changing the HTTP contract.
- Canonical activity definitions live in `activities` (migration `000030`) and are updated only when the client has the `define` or `all` scope.
- `contextAgents` and `contextGroups` are valid on 2.0 requests only. Their IFIs are denormalized into `statement_agents` so `related_agents` can match them. Signed statements are compact JWS (`RS256`, `RS384`, `RS512`). 2.0 requests must include an `x5c` chain; the chain is checked for time and issuer signatures. A trusted public root is not required, because conformance suites use their own certificates.

## Consequences

`make xapi conformance` runs the ADL LRS conformance test suite (`AUTH=keyId:secret`, `VERSION=1.0.3` or `2.0.0`) and is the check that this surface still matches the spec. The suite is not part of `make test`.

`related_activities` uses `activity_ids` plus the context-activity columns. That is enough for conformance and for moderate tenants. It is not a substitute for the partitioning discussion in ADR-0006.
