# ADR-0001: Storage Strategy — Postgres-first, MongoDB optional via Provider

## Status
Accepted (2026-01-23)

## Kontext
LRSolid ist ein modernes, Open-Source Learning Record Store (LRS) mit Fokus auf:
- xAPI-konforme Speicherung und Abfrage von Statements (write-heavy, bursty)
- zusätzliche xAPI APIs (State, Agent Profile, Activity Profile, Attachments)
- Analytics-first UX (Custom Charts), ggf. ergänzt durch Search/Indexing (z. B. OpenSearch)
- OSS-Installierbarkeit (Self-hosting, Uni/Enterprise)

Es wurde diskutiert, ob als primärer Datenspeicher MongoDB (JSON-Dokumente) oder PostgreSQL verwendet werden soll und ob beide unterstützt werden können.

## Entscheidung
Wir fokussieren initial auf **PostgreSQL (JSONB)** als *Source of Truth* und implementieren Storage über ein **Provider/Adapter-Interface**, sodass MongoDB später als alternativer Provider ergänzt werden kann.

**Kurzform:**
- **Postgres-first** für MVP und frühe Releases.
- **Storage Provider Architektur** von Anfang an, aber MongoDB erst später.
- **Kanonische Query-Semantik** (Cursor-based Pagination) wird im Core festgelegt, Provider müssen sie einhalten.

## Begründung
Postgres ist für LRSolid als primärer Store im MVP vorteilhaft, weil:

1. **Konsistenz & Integrität**
    - Eindeutige Statement IDs, Idempotency und State/Profile Semantik lassen sich mit Constraints/Transaktionen robust umsetzen.

2. **Planbare Performance**
    - Write-heavy Workloads (XR Sessions) sind mit Batch Inserts, Indizes und ggf. Partitionierung gut beherrschbar.

3. **Hybrid Schema (JSONB + Spalten)**
    - Für häufige Filter (actor/verb/object/stored_at) werden Spalten + B-Tree Indizes genutzt.
    - Das vollständige Statement bleibt als JSONB erhalten (GIN Index optional).

4. **Analytics-Ökosystem**
    - SQL ist der Standard für Debugging, Ad-hoc Analysen, Views/Materialized Views, Exporte und BI-Integrationen.
    - Für OSS-User ist Postgres in der Regel “boring & available”.

MongoDB bleibt eine valide Option, würde aber im MVP:
- zusätzliche Implementations- und Test-Komplexität erzeugen,
- Semantik-Unterschiede (Sortierung/Pagination/Transactions) in Conformance/Edge-Cases riskieren,
- den Fokus von Core-Features abziehen.

## Architektur-Implikationen
### Storage Provider Interface
Der Core definiert Ports/Interfaces (z. B. `StatementStore`, `StateStore`, `ProfileStore`, `AttachmentMetaStore`) und eine **kanonische Semantik** für:
- Sorting (stored_at + id tie-breaker)
- Cursor-based Pagination (kein Offset)
- since/until Verhalten
- “more”-Token (xAPI paging)

Implementierungen:
- `store/postgres` (MVP)
- `store/mongo` (optional später)

### Cursor-based Pagination (Pflicht)
Offset-Pagination wird vermieden, da sie bei großen Datenmengen teuer ist und zwischen Providern schwer konsistent zu halten ist.
Cursor basiert auf `(stored_at, id)`.

### Optional: Index/Search Layer
Für flexible Queries und UI-Analytics kann ein separater Index (z. B. OpenSearch) genutzt werden.
Postgres bleibt Source of Truth; Index ist abgeleitet und kann jederzeit neu aufgebaut werden.

## Konsequenzen
### Positiv
- Schnellere MVP-Lieferung bei hoher Robustheit.
- Saubere Semantik-Grundlage für spätere Provider.
- Gute Basis für Analytics, Exporte und Self-hosting.

### Negativ / Trade-offs
- MongoDB-User müssen initial Postgres nutzen.
- Provider-Abstraktion erfordert zusätzliche Design-Disziplin (Contracts, Tests).
