# ADR-0002: xAPI Statement Schema — Spaltenextraktion und Denormalisierung

## Status
Accepted (2026-04-10)

## Kontext

xAPI 1.0.3 Statements sind strukturell komplex. Analyse von drei realen Statements aus dem OmiLAXR/RWTH-Kontext (VR Serious Games) hat gezeigt, dass:

- Actor-Identifikatoren in vier verschiedenen IFI-Typen kommen können (`mbox`, `mbox_sha1sum`, `openid`, `account`)
- Actors sowohl `Agent` als auch `Group` (mit `member[]`-Array) sein können
- `result` mit `completion`, `success` und `score` für Analytics-Dashboards essenziell ist
- `context.registration` häufig genutzt wird, um Statements einer Session zuzuordnen
- `context.contextActivities` (parent/grouping/category) für Kurs-basierte Auswertungen relevant ist
- `object.objectType` für xAPI-Konformität (Voiding via `StatementRef`) zwingend nötig ist
- Extension-Werte aus der Praxis Datenqualitätsprobleme aufweisen (doppeltes JSON-Encoding, Strings statt Null)

Das initiale Schema (nur `actor_mbox`, `verb_id`, `object_id`) deckt diese Realität unzureichend ab.

## Entscheidung

Das Statements-Schema extrahiert alle xAPI-Felder als Spalten, die für **Filterung oder Analytics** relevant sind. Das vollständige Statement bleibt als `jsonb`-Spalte erhalten (Source of Truth). Felder, die nur zur Anzeige dienen oder tief verschachtelt sind, verbleiben in JSONB mit GIN-Index.

### Extrahierte Spalten

| Kategorie | Spalten |
|---|---|
| Timestamps | `stored_at`, `activity_at` (statement.timestamp) |
| Actor | `actor_type`, `actor_mbox`, `actor_mbox_sha1sum`, `actor_openid`, `actor_account_home`, `actor_account_name`, `actor_sha256` |
| Verb | `verb_id` |
| Object | `object_type`, `object_id`, `activity_type` (definition.type) |
| Context | `registration`, `context_platform`, `context_parent_ids[]`, `context_group_ids[]`, `context_category_ids[]` |
| Result | `result_completion`, `result_success`, `result_score_scaled`, `result_duration` |
| Voiding | `voided` |

### Bewusst in JSONB belassen

- `verb.display` (Sprachkarten, nur Anzeige)
- `object.definition.name/description` (mehrsprachig, kein Filter)
- `context.instructor` / `context.team` (selten gefiltert)
- `result.extensions` / `context.extensions` / `object.definition.extensions` (domain-spezifisch, GIN-Index genügt)
- `authority` (Audit-Zwecke, kein Analytics-Use-Case)

### Group-Actor Denormalisierung (`statement_agents`)

xAPI erlaubt `Group`-Actors mit `member[]`-Arrays. Ein Query wie "alle Statements von alice@example.org" muss auch Statements finden, in denen Alice Mitglied einer Gruppe ist. Dafür wird eine separate Tabelle `statement_agents` geführt, die alle Agenten eines Statements (Gruppe selbst + alle Member) flach hält. Dieses Muster entspricht Learning Lockers `agents`-Array.

### Voiding

Statements mit `verb.id = "http://adlnet.gov/expapi/verbs/voided"` und `object.objectType = "StatementRef"` setzen `voided = true` auf dem referenzierten Statement. Voidete Statements dürfen per xAPI-Spec nicht mehr zurückgegeben werden (außer explizit angefragt).

## Begründung

**Warum Spalten statt reines JSONB?**
- Gefilterte Queries (WHERE actor_mbox = ...) nutzen B-Tree-Indizes — Größenordnungen schneller als GIN-Scans auf JSONB
- Analytics-Aggregationen (`GROUP BY verb_id`, `AVG(result_score_scaled)`) sind auf Spalten deutlich effizienter
- Der Analytics-Service kann direkt auf Spalten joinen, ohne JSONB zu parsen

**Warum nicht alles extrahieren?**
- Extensions sind domain-spezifisch und nicht vorhersehbar — GIN-Index auf JSONB ist flexibler
- Language Maps (`verb.display`, `object.definition.name`) werden nur zur Anzeige gebraucht, nie gefiltert
- JSONB als Source of Truth ermöglicht jederzeit Nachextraktion ohne Datenverlust

**Datenqualität aus der Praxis (OmiLAXR)**
Reale Statements zeigen konsistente Muster:
- `"null"` als String statt JSON `null`
- Doppeltes JSON-Encoding (`"\"value\""`)
- Numerische Werte als Strings (`"72"`)

Diese Normalisierung ist Aufgabe des **Analytics-Service** (beim Konsumieren aus Kafka), nicht des LRS-Ingest-Pfads. Der LRS speichert Statements so wie sie ankommen (Spec-Anforderung).

## Konsequenzen

### Positiv
- Alle xAPI 1.0.3 Actor-IFI-Typen sind filterbar und indexiert
- xAPI-Konformität durch Voiding-Support
- Analytics-Dashboard kann direkt auf extrahierten Spalten arbeiten
- Group-Member-Lookup funktioniert ohne Full-JSONB-Scan

### Negativ / Trade-offs
- Service-Layer (`lrs/service.go`) muss alle Felder beim Ingest parsen und extrahieren
- `statement_agents` erfordert zusätzliche INSERTs pro Group-Statement
- Datenqualitätsprobleme (doppeltes Encoding) müssen im Analytics-Service normalisiert werden, nicht im LRS
