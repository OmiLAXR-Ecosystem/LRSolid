# ADR-0005: SSO Login via OpenID Connect and Shibboleth (SAML 2.0)

## Status
Proposed (2026-10-08)

## Context

LRSolid currently supports a single login mechanism for human users: email + password
(`POST /api/auth/login`, bcrypt, HS256 JWT in the `lrsolid_session` httpOnly cookie, 24 h TTL).
Universities and enterprises that self-host an LRS almost always require federated login:

- **OpenID Connect (OIDC)** — Keycloak, Microsoft Entra ID, Google Workspace, Okta, Authentik, and
  also Shibboleth IdP ≥ 4 with the OIDC OP plugin.
- **Shibboleth** — the de-facto SAML 2.0 stack in higher education (DFN-AAI, SWITCHaai, eduGAIN,
  InCommon). "Shibboleth login" means: LRSolid acts as a **SAML 2.0 Service Provider (SP)**,
  the institution runs a Shibboleth **Identity Provider (IdP)**, attributes follow the
  eduPerson / SCHAC schema and are usually transported as OID-named attributes.

This ADR captures what is already in place, what is missing, and the steps to implement both.

## Inventory — what the codebase already provides

| Area | Finding | Impact |
|---|---|---|
| `users` table (`000006`) | Already has `password_hash NULL`, `auth_provider`, `auth_subject` + index `idx_users_auth`. Columns are **unused** in Go code. | Schema anticipated SSO. Can be used as-is for a single identity per user, or superseded by a `user_identities` table (see below). |
| `Login` (`internal/httpapi/auth.go`) | Rejects users with `password_hash IS NULL` with the same 401 as unknown users. | SSO-only users are already protected against password login. No change needed. |
| Session | `auth.GenerateToken` / `auth.Middleware` — stdlib HS256 JWT in cookie, claims `{sub,email,role,exp,iat}`. Role = org role in `cfg.DefaultOrg`, frozen for 24 h. | SSO callbacks can issue the **same cookie**; nothing downstream (REST handlers, `requireAdminClaims`, `XAPIClientAuth` cookie fallback) changes. |
| Org resolution at login | Login only looks at `cfg.DefaultOrg`. | SSO flow must carry the target org through the redirect round-trip (server-side request record). |
| Routing | Only `/api/auth/login` and `/logout` are public (`router.go`). Vite dev proxy and prod `nginx.conf` forward **all** of `/api/*` to Go. | Callback / ACS URLs can live under `/api/auth/...` and work identically in dev (`:5173`) and prod (`:80`). `APP_URL` is already the public base URL. |
| Secrets | `secrets.Store` (AES-encrypted values in Postgres, used for data-store DSNs and S3 credentials). | Reuse for OIDC client secrets and the SAML SP private key — no new secret infrastructure. |
| Org-scoped settings | `export_settings` per org with env seeding (`EXPORT_*`). | Precedent for an `auth_providers` table seeded from env. |
| Invites | `RestInviteUser` writes `user_invites` and mails `APP_URL/accept-invite?token=…`, but **no accept endpoint and no SPA route exist**. | Invite acceptance is unfinished. SSO provisioning should be the thing that finally consumes invites (JIT provisioning gated by a pending invite). |
| Frontend | `LoginView` renders hard-coded, disabled "Google" / "Microsoft" buttons. `AuthContext` calls `GET /api/auth/me` on mount. SPA uses hand-rolled path routing `/:org/:route` (`App.tsx`), no router library. | Post-redirect session pickup already works (cookie → `me()`). Buttons must become data-driven. |
| Config | Env-only (`internal/config`). | Add SSO env vars for seeding; runtime config belongs in DB + admin UI. |
| Dependencies | stdlib JWT only; no OAuth2/OIDC/SAML/XML-DSig libraries. | Must add libraries — writing XML-DSig / SAML parsing by hand is not an option. |
| Migrations | Latest is `000024` (AGENTS.md still says 14). | New migrations start at `000025`. |

## Decision

Implement SSO as a **provider-pluggable login layer** in a new package `internal/sso` that
terminates in the existing session cookie. Two provider types in scope:

1. `oidc` — Authorization Code Flow + PKCE, via `github.com/coreos/go-oidc/v3` + `golang.org/x/oauth2`.
2. `saml` — SAML 2.0 SP (HTTP-Redirect for AuthnRequest, HTTP-POST for Response), via
   `github.com/crewjam/saml`. "Shibboleth" is a configuration profile of this type (eduPerson
   attribute mapping, IdP metadata from federation, SP metadata publication).

Provider configurations are stored **per organisation** in Postgres (nullable `org_id` = global),
secrets in `secrets.Store`, and managed from the Settings UI. Env variables may seed one OIDC
and one SAML provider for the default org on first start (same pattern as export settings).

Local password login stays available but becomes disable-able per org (`local_login_enabled`).

## Needs

### N1 — Libraries (Go)

| Purpose | Library | Notes |
|---|---|---|
| OIDC discovery, JWKS, ID-token verification | `github.com/coreos/go-oidc/v3` | Handles `.well-known/openid-configuration`, key rotation, `iss`/`aud`/`exp`/`nonce` checks. |
| OAuth2 code exchange, PKCE | `golang.org/x/oauth2` | `oauth2.S256ChallengeOption`, `VerifierOption`. |
| SAML 2.0 SP | `github.com/crewjam/saml` | SP metadata generation, AuthnRequest, Response/Assertion validation, XML-DSig, encrypted assertions, IdP metadata fetch (`samlsp.FetchMetadata`). Use the low-level `saml.ServiceProvider`, not `samlsp.Middleware`, so we can plug into our own session cookie. |

No frontend library is needed — the browser is only redirected.

### N2 — Data model (new migrations)

**`000025_auth_providers`**

```sql
CREATE TABLE auth_providers (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id        uuid NULL REFERENCES organisations(id) ON DELETE CASCADE, -- NULL = global
  slug          text NOT NULL,              -- used in URLs: /api/auth/sso/{slug}/...
  type          text NOT NULL CHECK (type IN ('oidc','saml')),
  display_name  text NOT NULL,              -- "Continue with <display_name>"
  enabled       boolean NOT NULL DEFAULT true,
  config        jsonb NOT NULL,             -- non-secret settings, see below
  secret_ref    text NULL,                  -- key in secrets.Store (client secret / SP private key)
  auto_provision boolean NOT NULL DEFAULT false,
  default_role  text NOT NULL DEFAULT 'viewer' CHECK (default_role IN ('owner','admin','member','viewer')),
  link_by_email boolean NOT NULL DEFAULT false,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (org_id, slug)
);
```

`config` (OIDC): `issuer`, `client_id`, `scopes` (default `openid profile email`), `claim_mappings`
(`subject: sub`, `email: email`, `display_name: name`, `groups: groups`), `role_mapping`
(`{ "lrs-admins": "admin", "*": "viewer" }`), `require_email_verified: true`.

`config` (SAML): `idp_metadata_url` **or** `idp_metadata_xml`, `sp_entity_id`
(default `APP_URL/api/auth/saml/{slug}/metadata`), `sp_cert_pem` (public; key via `secret_ref`),
`name_id_format`, `attribute_mappings` (defaults = Shibboleth/eduPerson OIDs, see N5),
`role_mapping` on `eduPersonAffiliation` / `eduPersonEntitlement` / `isMemberOf`,
`sign_requests: true`, `want_assertions_encrypted: false`, `allow_idp_initiated: false`.

**`000026_user_identities`** — replaces the single `auth_provider/auth_subject` pair so a user can
hold several identities (local password + Shibboleth + Entra ID):

```sql
CREATE TABLE user_identities (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id       uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  provider_id   uuid NOT NULL REFERENCES auth_providers(id) ON DELETE CASCADE,
  subject       text NOT NULL,              -- OIDC `sub` / SAML NameID or subject-id
  email         text NULL,
  attributes    jsonb NOT NULL DEFAULT '{}', -- last received claims/attributes (debugging, role sync)
  last_login_at timestamptz NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (provider_id, subject)
);
-- data migration: copy users.auth_provider/auth_subject into user_identities where set;
-- keep old columns for one release, drop in a later migration.
```

**`000027_auth_requests`** — server-side storage of in-flight login attempts and SAML replay cache:

```sql
CREATE TABLE auth_requests (
  id           text PRIMARY KEY,            -- OIDC `state` / SAML AuthnRequest ID
  provider_id  uuid NOT NULL REFERENCES auth_providers(id) ON DELETE CASCADE,
  org_id       uuid NULL,
  nonce        text NULL,                   -- OIDC
  pkce_verifier text NULL,                  -- OIDC
  return_to    text NOT NULL DEFAULT '/',   -- validated relative path
  created_at   timestamptz NOT NULL DEFAULT now(),
  expires_at   timestamptz NOT NULL         -- ~10 min
);
CREATE TABLE saml_seen_assertions (
  assertion_id text PRIMARY KEY,
  expires_at   timestamptz NOT NULL         -- = NotOnOrAfter
);
```

Why server-side instead of a state cookie: the SAML HTTP-POST binding is a **cross-site POST**
from the IdP to `/acs`. A `SameSite=Lax` cookie (our current default) is **not sent** on that
request; `SameSite=None` would weaken the session cookie. A DB record keyed by request ID
avoids the problem for both protocols and gives replay protection for free.

### N3 — Backend endpoints (`internal/httpapi/sso.go`, registered in `router.go`)

Public (no session):

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/api/auth/providers?org={slug}` | List enabled providers for the login page: `[{slug,type,displayName}]` + `localLoginEnabled`. |
| `GET` | `/api/auth/sso/{slug}/start?return_to=/default/statements` | Create `auth_requests` row, 302 to IdP (OIDC auth URL with `state`,`nonce`,`code_challenge`; SAML AuthnRequest via HTTP-Redirect with `RelayState = request id`). |
| `GET` | `/api/auth/oidc/{slug}/callback` | Verify `state`, exchange code (PKCE), verify ID token (`go-oidc`), optionally call UserInfo, run identity resolution (N4), set `lrsolid_session`, 302 to `return_to`. On failure 302 to `/login?error=…`. |
| `POST` | `/api/auth/saml/{slug}/acs` | Parse `SAMLResponse`, validate signature/conditions/audience/`InResponseTo` against `auth_requests`, check replay cache, map attributes, identity resolution, set cookie, 302. |
| `GET` | `/api/auth/saml/{slug}/metadata` | SP metadata XML (entityID, ACS, signing cert, `mdui:UIInfo`, `RequestedAttribute`s). Needed for registration with the IdP / federation. |
| `POST` | `/api/auth/saml/{slug}/slo` | (V2) Single Logout endpoint. |

Protected (admin, under `/api/v1/{org}`):

| Method | Path | Purpose |
|---|---|---|
| `GET` / `POST` | `/auth-provider` | List / create. |
| `PATCH` / `DELETE` | `/auth-provider/{id}` | Update / delete (secret rotation via `secret_ref`). |
| `POST` | `/auth-provider/{id}/test` | OIDC: fetch discovery + JWKS. SAML: fetch/parse IdP metadata, report entityID, SSO URLs, cert expiry. |
| `GET` | `/auth-provider/{id}/sp-metadata` | Same as public metadata, for the UI download button. |

Changes to existing endpoints:

- `POST /api/auth/login` — return 403 `local login disabled` when the org's `local_login_enabled = false`.
- `GET /api/auth/me` — add `authProvider` so the UI can hide "change password" for SSO users.
- `GET /api/v1/{org}/user` — include identity provider badges.

### N4 — Identity resolution & provisioning (`internal/sso/resolve.go`)

Shared by both protocols; input is a normalized `Identity{ProviderID, Subject, Email, EmailVerified, DisplayName, Groups []string, Raw map}`.

1. `user_identities` lookup by `(provider_id, subject)` → existing user. Reject if `users.disabled_at IS NOT NULL`.
2. Else, if `link_by_email` and `EmailVerified` and a `users` row with that email exists → create `user_identities` row, continue with that user.
3. Else, if a non-expired, unaccepted `user_invites` row exists for `(email, org)` → create user (`password_hash NULL`), create identity, create `org_memberships` with the invite role, set `accepted_at`.
4. Else, if `auto_provision` → create user + identity + `org_memberships` with `default_role` (or role from `role_mapping`).
5. Else → redirect to `/login?error=no_account`.
6. Role sync: if `role_mapping` is configured and matches, upsert `org_memberships.role` on every login; otherwise never touch an existing membership.
7. Issue session: `auth.GenerateToken(cfg.JWTSecret, Claims{UserID, Email, Role}, sessionTTL)`. Optionally cap TTL to SAML `SessionNotOnOrAfter` / OIDC `exp` when present.

Email is **not** a stable identifier; the subject is. For Shibboleth prefer `subject-id` / `pairwise-id`
/ `eduPersonPrincipalName` over transient NameIDs (reject `transient` NameID unless an explicit
persistent attribute is mapped).

### N5 — Shibboleth-specific requirements

These go beyond "generic SAML" and are what institutions will ask for:

- **Attribute names are OIDs**, default mapping:
  - subject: `urn:oasis:names:tc:SAML:attribute:subject-id` → fallback `urn:oid:1.3.6.1.4.1.5923.1.1.1.6` (eduPersonPrincipalName) → fallback persistent NameID
  - email: `urn:oid:0.9.2342.19200300.100.1.3` (mail)
  - display name: `urn:oid:2.16.840.1.113730.3.1.241` (displayName), fallback `urn:oid:2.5.4.42` + `urn:oid:2.5.4.4` (givenName + sn)
  - affiliation: `urn:oid:1.3.6.1.4.1.5923.1.1.1.9` (eduPersonScopedAffiliation), `…1.1.1.1` (eduPersonAffiliation)
  - entitlement/groups: `urn:oid:1.3.6.1.4.1.5923.1.1.1.7` (eduPersonEntitlement), `urn:oid:1.3.6.1.4.1.5923.1.5.1.1` (isMemberOf)
  - Note: Shibboleth IdPs release `mail` as **not verified** semantics; treat SAML email as verified only if the provider config says so (`trust_email: true`, default true for SAML since release is controlled by the IdP operator).
- **SP metadata** must be publishable and stable: fixed `entityID`, long-lived self-signed SP cert (10 y typical), `mdui:DisplayName/Description/Logo/PrivacyStatementURL`, `RequestedAttribute` list, `NameIDFormat` list. Federations (DFN-AAI, eduGAIN) require registering this metadata; attribute release is often tied to the **REFEDS R&S** entity category — document that LRSolid requests only R&S attributes.
- **IdP metadata**: load from URL with periodic refresh (`validUntil`/`cacheDuration`) and signature check against the federation signing cert; or paste XML for a single IdP. Multi-IdP (federation aggregate / MDQ) and a discovery service (WAYF) are **out of scope for V1**; V1 = one IdP per provider record. Multiple Shibboleth providers can be configured as separate records.
- **Signing**: sign AuthnRequests (many IdPs require it); accept signed Response or signed Assertion; support encrypted assertions (SP key via `secret_ref`).
- **Clock skew** tolerance (±3 min) on `NotBefore`/`NotOnOrAfter`; **replay cache** on assertion ID.
- **Shibboleth IdP as OIDC OP**: if the institution runs the Shibboleth OIDC plugin, the `oidc` provider type covers it with zero SAML work. Offer this as the preferred path in docs.

### N6 — Security requirements

- OIDC: `state` (CSRF), `nonce` (ID-token replay), PKCE S256, verify `iss`, `aud == client_id`, `exp`, `at_hash` if applicable; require `email_verified` when configured; JWKS rotation handled by `go-oidc`.
- SAML: validate XML signature on Response or Assertion, `Destination == ACS URL`, `Audience == sp_entity_id`, `InResponseTo` matches an `auth_requests` row (reject unsolicited/IdP-initiated unless enabled), `SubjectConfirmationData.Recipient/NotOnOrAfter`, replay cache.
- `return_to` must be a **relative path** starting with `/` and not `//` (open-redirect guard).
- Callback and ACS endpoints: rate-limit per IP, log outcome (provider, subject hash, result) for audit; never log tokens/assertions at info level.
- Secrets (client secret, SP private key) only via `secrets.Store`; API responses expose `hasSecret: true`, never the value.
- `auth_requests` / `saml_seen_assertions` need a periodic cleanup (piggy-back on the stats-rollup ticker or a small janitor goroutine).
- Keep session cookie attributes unchanged (`HttpOnly`, `Secure` outside dev, `SameSite=Lax`, `Path=/`).
- Reverse proxy: redirect URIs are built from `cfg.AppURL`, not from `Host` headers, so header spoofing cannot alter them. Document that `APP_URL` must be the public HTTPS URL in production.

## Steps (implementation order)

### Phase 1 — Foundation + OIDC (ships value fastest, covers Shibboleth-OIDC installations)

1. Add dependencies: `go get github.com/coreos/go-oidc/v3 golang.org/x/oauth2`.
2. Migrations `000025_auth_providers`, `000026_user_identities` (incl. data copy from `users.auth_provider/auth_subject`), `000027_auth_requests`.
3. `internal/models`: `AuthProvider`, `UserIdentity`; `internal/sso`: `Provider` interface (`Start(ctx, req) (redirectURL, error)`, `Callback(ctx, r) (Identity, requestID, error)`), `Identity`, `Resolve()` (N4), request store, janitor.
4. `internal/sso/oidc`: provider implementation with discovery cache, PKCE, nonce, claim mapping, UserInfo fallback.
5. `internal/httpapi/sso.go`: `/providers`, `/sso/{slug}/start`, `/oidc/{slug}/callback`; register in `router.go`. `return_to` validation. Error redirect convention.
6. Admin CRUD + `/test` endpoints; env seeding in `main` startup (same place export settings are seeded).
7. Extend `/api/auth/me` and `/login` (local-login toggle).
8. Frontend: `listProviders`, data-driven `LoginView`, `/login` and error banner, Settings "Authentication" section (OIDC form), user badges.
9. Dev compose profile with Keycloak/Dex; Go tests (mock OP, resolver); router tests; Bruno collection; README/OpenAPI.

### Phase 2 — SAML 2.0 / Shibboleth

10. `go get github.com/crewjam/saml`.
11. `internal/sso/saml`: SP key/cert handling (upload or generate), IdP metadata loader with refresh + signature verification, AuthnRequest (HTTP-Redirect, signed), ACS validation (`InResponseTo`, audience, destination, conditions, replay), eduPerson default attribute mapping (N5), NameID policy.
12. Endpoints `/saml/{slug}/acs` (POST) and `/saml/{slug}/metadata` (GET) incl. `mdui` and `RequestedAttribute`s.
13. Settings UI: SAML form (metadata URL/XML, attribute mapping editor, SP cert/key, metadata download, test).
14. Dev compose: Keycloak-as-SAML-IdP or SimpleSAMLphp test IdP; documented recipe against a real Shibboleth IdP with eduPerson attributes.
15. Tests: signed fixture responses, negative cases, metadata rendering snapshot.
16. README "Shibboleth / DFN-AAI" guide.

### Phase 3 — Hardening & conveniences

17. Finish `/accept-invite` for local login (set password) so invites work for both paths.
18. OIDC RP-initiated logout and SAML SLO (optional, per provider flag).
19. Role sync from groups/affiliations on each login; audit log table for login events.
20. Multi-IdP via federation aggregate / MDQ + embedded discovery (WAYF) — only if an institution needs more than a handful of IdPs.
21. Drop legacy `users.auth_provider/auth_subject` columns once all deployments have migrated.

## Consequences

### Positive
- Institutions can onboard without managing LRSolid passwords; invites become usable.
- Session handling, authorization, and xAPI auth are untouched — SSO is purely an additional way to mint the existing cookie.
- Per-org providers fit the existing `Organisation → Project → LRS` model and the export-settings precedent.

### Negative / trade-offs
- Two new third-party dependencies with security-critical surface (XML-DSig in particular); pin versions and watch advisories.
- SAML adds operational burden (SP certificate lifecycle, federation registration, metadata refresh) that needs clear docs.
- Role in the JWT is still frozen for 24 h; role changes from the IdP apply on next login (same as today for local roles).
- Server-side `auth_requests` adds two small tables and a cleanup job.

## Open questions

1. Provider scope: strictly per org, or also truly global providers (`org_id NULL`) that map users into `DefaultOrg`? (Draft assumes both.)
2. Provisioning default: should `auto_provision` default to **off** (invite-only) for universities? Draft says off.
3. Should the hard-coded "Google" / "Microsoft" buttons stay as preconfigured OIDC presets (issuer templates) in the Settings UI?
4. Is Single Logout a requirement for the first Shibboleth deployment, or is local logout acceptable?
5. Target federation(s) for the first deployment (DFN-AAI? eduGAIN?) — determines metadata signing cert and entity categories to document.
