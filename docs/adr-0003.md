# ADR-0003: Analytics-Architektur — Kafka + ClickHouse/TimescaleDB

## Status
Proposed (2026-04-10)

## Kontext

LRSolid soll neben dem LRS-Core (Statements speichern und abfragen) ein **Analytics-Modul** bekommen, das Auswertungen auf einem Dashboard darstellt (z. B. Completion-Rates, Score-Verteilungen, Verb-Häufigkeiten, Session-Dauern).

Anforderungen:
- Tausende Statements pro Sekunde Ingest-Durchsatz
- Analytics-Queries sollen die LRS-Performance nicht beeinflussen
- Zukünftig können mehrere unabhängige Services Statements konsumieren (Analytics, Notifications, Export)
- Das System soll erweiterbar sein ohne den LRS-Core anzufassen

PostgreSQL allein als Analytics-Store hat Grenzen:
- Schwere Aggregations-Queries (`GROUP BY`, `AVG`, Window Functions über Millionen Rows) belasten denselben Datenbankserver wie der Ingest-Pfad
- Columnar Storage (wie ClickHouse) ist für Aggregationen über große Datenmengen Größenordnungen schneller

## Entscheidung

Eine **dreischichtige Analytics-Architektur**:

```
xAPI Clients
     │
     ▼
┌─────────────────────────────┐
│  LRS (Go API)               │
│  POST /xapi/statements      │
└──────────────┬──────────────┘
               │ 1. Schreibt Statement
               ▼
       ┌───────────────┐
       │  PostgreSQL   │  ← Source of Truth (xAPI-konform)
       │  (statements) │
       └───────┬───────┘
               │ 2. Outbox → Kafka (CDC oder Poller)
               ▼
        ┌─────────┐
        │  Kafka  │  ← Event-Bus (statement.stored Events)
        └────┬────┘
             │ 3. Konsumiert
             ▼
┌─────────────────────────┐
│  Analytics Service (Go) │  ← normalisiert, aggregiert
└────────────┬────────────┘
             │ 4. Schreibt Aggregationen
             ▼
   ┌──────────────────────┐
   │  ClickHouse oder     │  ← Analytics Store (columnar)
   │  TimescaleDB         │
   └──────────────────────┘
             │
             ▼
     Dashboard API → SolidJS Frontend
```

### Kafka als Event-Bus

Kafka entkoppelt den LRS-Ingest-Pfad vom Analytics-Processing. Der LRS muss nicht wissen, welche Downstream-Services existieren. Neue Consumer (z. B. Notification-Service, Export-Service) können ohne Änderung am LRS ergänzt werden.

**Outbox-Pattern:** Das Statement wird in PostgreSQL gespeichert und gleichzeitig in einer `outbox`-Tabelle in derselben Transaktion geloggt. Ein separater Poller (oder Debezium/CDC) publiziert die Outbox-Einträge nach Kafka. Damit ist garantiert, dass kein Statement zwischen DB-Write und Kafka-Publish verloren geht.

### Analytics Store: ClickHouse vs. TimescaleDB

| Kriterium | ClickHouse | TimescaleDB |
|---|---|---|
| Aggregations-Performance | Sehr hoch (columnar) | Gut (Postgres-Extension) |
| Setup-Aufwand | Eigener Service | Nur Postgres-Extension |
| SQL-Kompatibilität | Eigener Dialekt | Vollständiges PostgreSQL |
| Horizontales Scaling | Native Sharding | Eingeschränkt |
| Ops-Komplexität | Höher | Niedrig |

**Empfehlung: TimescaleDB für den Einstieg.** Es ist eine PostgreSQL-Extension — kein neuer Infrastrukturkomponent. Wechsel zu ClickHouse ist möglich wenn Query-Performance tatsächlich zum Problem wird (datenmengengetriebene Entscheidung).

### Analytics-Service Aufgaben

Der Analytics-Service (separates Go-Binary) konsumiert Statement-Events aus Kafka und:

1. **Normalisiert** Datenqualitätsprobleme aus der Quelle:
   - Doppeltes JSON-Encoding (`"\"value\""` → `"value"`)
   - `"null"`-Strings → echte Null
   - Numerische Strings (`"72"` → `72`)
   - Platform-Strings parsen (`UnityWindowsEditorv6000.0.40f1::OmiLAXR.xAPIv2.1.1::...`)

2. **Schreibt** in den Analytics-Store:
   - Flache Zeilen mit extrahierten Feldern für schnelle Aggregationen
   - Keine Raw-JSONB-Speicherung nötig (PostgreSQL hat das bereits)

3. **Verwaltet** vorberechnete Aggregationen oder Materialized Views

## Begründung

**Warum Kafka statt direkte DB-Queries auf PostgreSQL?**
- Entkopplung: LRS und Analytics können unabhängig skaliert, deployed und gewartet werden
- Replay: Kafka ermöglicht es, den Analytics-Store jederzeit neu aufzubauen (Reprocessing)
- Fan-out: Mehrere Consumer ohne Mehraufwand am LRS
- Backpressure: Analytics-Processing kann langsamer sein als Ingest ohne den LRS zu blockieren

**Warum nicht MongoDB?**
- PostgreSQL + JSONB deckt die Flexibilität von MongoDB für diesen Use-Case ab
- ACID-Garantien, Row-Level-Security und Cursor-Pagination sind in PostgreSQL besser etabliert
- Ein zusätzlicher Mongo-Stack würde Komplexität ohne klaren Mehrwert hinzufügen

**Warum nicht ClickHouse direkt als LRS-Store?**
- ClickHouse hat keine ACID-Transaktionen und kein Single-Row-Upsert (benötigt für xAPI Idempotency)
- xAPI-Konformität erfordert UPDATE (Voiding), was in ClickHouse aufwändig ist
- ClickHouse ist ein Analytics-Store, kein transaktionaler Store

**Warum PostgreSQL als Source of Truth beibehalten?**
- Alle xAPI-APIs (State, Profile, Attachments) bleiben in PostgreSQL
- Voiding, Idempotenz, Konfliktbehandlung funktionieren mit ACID
- Self-hosting ist mit einem Postgres-Stack einfacher als mit Kafka + ClickHouse + Postgres

## Konsequenzen

### Positiv
- LRS-Performance bleibt unberührt von Analytics-Queries
- Analytics-Stack kann unabhängig skaliert werden
- Reprocessing bei Schema-Änderungen möglich (Kafka Replay)
- Erweiterbar für zukünftige Consumer (Notifications, Export, Compliance)

### Negativ / Trade-offs
- Kafka erhöht Infrastruktur-Komplexität (vor allem für Self-hosting)
- Eventual Consistency: Dashboard-Daten haben leichte Verzögerung gegenüber LRS-Daten
- Outbox-Poller ist ein zusätzlicher Failure-Point (muss monitored werden)
- Für sehr kleine Deployments (< 100k Statements/Tag) ist die Architektur überdimensioniert — direktes SQL auf PostgreSQL wäre dort ausreichend
